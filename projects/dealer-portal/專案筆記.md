### 產品、使用者與流程

- **F01（用戶回述，2026-09-21）**：Dealer Portal 是第一個要建立的真實作品集案例。
- **F02（用戶回述，2026-09-21）**：主要使用者是 e-bike 經銷商技師；在銷售後保養與維修時，需要排查錯誤、修復、更新與設定車主偏好。
- **F03（用戶回述，2026-09-21）**：整體任務是先診斷車輛，再依排解指南修復問題或更新韌體，最後啟用車輛並完成必要設定。各情境分支、觸發條件與是否每次都需啟用車輛尚待確認。
- **F04（用戶回述，2026-09-21）**：重構後的 Dealer Portal 包含 Service Tool、Claim and Order 與 Knowledge Base。Claim and Order 用於確定零件無法排除修復後的保固索賠或購買；Knowledge Base 支援售服團隊維護指南、文件與影片，並讓 Service Tool 依問題提供資源。跨模組機制尚待探索。

### 舊版 Service Tool 的問題

- **F05（用戶回述，2026-09-21）**：前身 Hyena Service Tool 採關卡式檢測與更新；問題需先處理才能繼續，如果在早期關卡卡住，技師難以先掌握全車問題或優先處理急迫任務。系統擴充後關卡變多，團隊因此決定重構。
- **F06（用戶回述，2026-09-21）**：無法快速掌握全車問題，會影響向客戶回報與安排維修；卡關說明不足使技師改向售服團隊詢問。目前沒有量化資料或研究原始紀錄。
- **F07（用戶回述，2026-09-21）**：彈窗篇幅限制排解指引；模組增加使強制路徑更長，也提高調整與維護成本。
- **F08（用戶回述，2026-09-21）**：Dashboard 以部件序號與韌體版本等身分資訊為主，Advanced Diagnosis 與 Help Center 不顯眼；排解資源分散在線下推廣、YouTube 與內嵌手冊。這些是任務相關性的判斷，不代表身分資訊完全無用。
- **F09（用戶確認，2026-09-21）**：沒有「技師放棄診斷」的比例資料，不得聲稱或暗示存在未公開的流失率。
- **F10（用戶回述，2026-09-21）**：`Skip for now` 是使用者卡關後追加的補救，只適用於系統錯誤碼檢查。更新失敗進入 bootloader mode 等狀態仍需先處理才能繼續；不能寫成所有關卡都能或都不能跳過。
- **F11（用戶回述，2026-09-21）**：利害關係人包含技師、售服支援、產品與工程。原稿的角色引言與「我想修復馬達，但被卡在無關檢測」來源不明，不當作受訪者逐字引言。

### 新版 Overview

- **F16（用戶確認，2026-09-21）**：新版連車後的 Overview 對應前身 Dashboard；本輪提供 A08–A12 五張畫面。
- **O01（畫面觀察，2026-09-21，A08–A09）**：中央呈現車型、車輛識別、里程、下次保養、啟用日期、電池與增程電池電量，以及帶部件定位點的車圖；A09 顯示 Motor 部件浮層，含 Component Info 與 Critical 錯誤入口。觸發方式待確認。
- **O02（畫面觀察，2026-09-21，A08–A12）**：右側 Workspace 有 Good、Warning、Critical 與待診斷狀態圖例；A08 列出 Motor 錯誤與 HMI 韌體更新，並顯示 Full Diagnosis 2/10 及建立服務報告入口。A10 提醒完成診斷；A11 顯示 10/10 與建立報告提示；A12 顯示報告勾選圖示及 Workspace all clear 完成回饋。這些是狀態畫面，尚不能證明實際切換順序、狀態比例算法或報告建立的前置限制。

- **F17（用戶確認，2026-09-21）**：連車後系統會自動檢查，列出可偵測的零件異常錯誤碼及韌體更新需求。多數有感測器的零件可自動診斷，但部分檢查需要技師手動配合，例如轉動踏板以確認踏頻（cadence）感測器是否正常，因此提供 Full Diagnosis。
- **F18（用戶更正，2026-09-21）**：A08–A10 中的 Full Diagnosis「2/10」是設計稿誤植，該情境應約為「8/10」。此數字為用戶對情境的概略說明，不是固定自動診斷比例，也不是量化成效；素材仍保留原圖，對外使用前需修正或註明。
- **F19（用戶確認，2026-09-21）**：技師可自行選擇先處理哪個項目，例如先更新 HMI，並可從左側進入對應項目了解操作。部分業務邏輯仍有先後依賴，由系統判斷；未確認細節，不表述為所有操作均無限制。

### Workspace、處理方式與版面設計理由

- **F20（用戶回述，2026-09-21）**：Workspace 借用常見專案管理概念，集中管理該車所有待處理項目；Full Diagnosis 新發現的問題也會加入，用戶點擊項目可直接進入對應內容。
- **F21（用戶回述，2026-09-21）**：對應內容包含兩種處理方式：一種提供明確按鈕，由軟體執行更新或修復（A13–A16）；另一種提供明確步驟與教學影片，協助技師排解（A17）。用戶暫稱前者「操作指引」，命名及案例是否分開談尚在討論。
- **F22（用戶回述，2026-09-21）**：整體採左中右三欄：左側為可持續擴充的工具，中央隨任務替換內容，右側 Workspace 列出該車最重要的待處理維護事項。
- **F23（用戶回述，2026-09-21）**：經銷商同時維修其他系統的車，本系統也支援多個品牌與車款；使用者多為自行車商，未必具備專業 e-bike 維修經驗。因此在 Overview 以車圖搭配部件定位點，希望讓技師在類似大廳的入口更直覺地熟悉部件。這是設計理由，尚無理解效率或學習成效的驗證資料。
- **O03（畫面觀察，2026-09-21，A13–A17）**：更新與參數檢查畫面呈現執行入口及分項進度；排解指南同時包含文字步驟、影片與 Sensor Diagnosis 工具按鈕。因此兩類內容不宜僅以「有無按鈕」區分。任務完成確認原則見 F24；個別項目的移除／更新方式尚未細分。

- **F24（用戶回述，2026-09-21）**：任務完成確認可能依情境採不同方式，由「系統引導操作」與「逐步排解指南」各自描述；通常再執行一次 Full Diagnosis，系統即可確認問題是否排除。不能推定所有項目都會自動移除，或所有情境都必須重新完整診斷。

### Overview 替代方案與取捨

- **F25（用戶回述，2026-09-22，A18–A19）**：用戶對核心 Overview 嘗試多種 wireframe，並取得支援團隊回饋。「任務管理」看板方案極大化任務展示，但輔助工具過於隱藏、難以發揮作用；「工具與任務並列」方案羅列各式工具，早期任務以維修歷程呈現（用戶後續釐清，見 F27），利害關係人反饋任務資訊應優先於工具。這是團隊回饋，不等同技師使用者測試。
- **F26（用戶回述，2026-09-22）**：吸收回饋後，用戶將布局重點定為平衡任務查看與工具取得：讓使用者先意識到待辦任務，並能及時取得輔助工具，因此發展為現在的三欄式大廳。
- **O04（畫面觀察，2026-09-22，A19）**：左側為工具群組，右側大區域呈現車輛資訊及 Maintenance History；頂部另有切換 Task Dashboard 的文字。用戶已確認此維修歷程即當時所稱任務，見 F27。

- **F27（用戶釐清，2026-09-22）**：A19 中所稱任務就是維修歷程。早期直接展示所有服務紀錄，後來改為聚焦當下最新診斷，歷史回顧移至 Service Book。這是任務內容與資訊範圍的演變，不能只描述為側欄位置調整。
- **F28（用戶回述數據結論，2026-09-22）**：數據顯示技師查看、輸出 Service Book 的數量並不高。尚未取得原始數據、統計期間、使用人數／維修次數基準或預期目標，因此只保留此定性結論，不轉寫成低使用率、不推定原因，也不延伸為整體 Service Tool 成效。用戶稱輸出對象為 Service Book，與素材 Service Report 的命名關係尚未細分。
- **O05（畫面觀察，2026-09-22，A20–A21）**：本輪素材為 Service Report。可見發布、列印／下載選項，以及完成任務、部件更換歷程、剩餘任務、車輛／電池／騎乘資訊。報告含剩餘任務，因此不能僅憑先前全清狀態圖推定必須清除全部問題才能產出報告；實際條件仍待確認。

### Full Diagnosis 流程畫面

- **F34（用戶確認，2026-09-22，A25–A30）**：前兩張為診斷前與診斷後畫面，後四張為不同階段的檢測畫面，包含自動診斷及需要使用者輔助的診斷；附件排列不等同實際檢測順序。
- **O06（畫面觀察，2026-09-22，A25–A26）**：開始與摘要皆以雲端驗證、控制與顯示單元、驅動單元、電力供應四類組織。摘要呈現各類 Critical／Warning／Skip 數量與狀態圖環，並提供 View Detail、重跑診斷與 Resolve Task in Workspace 入口。控制與顯示類圖環含橘色，但 Warning 標示 0，屬素材待核對處，不據此推導算法。
- **O07（畫面觀察，2026-09-22，A27–A30）**：自動檢查畫面突出當前項目並顯示四類階段導覽；雲端驗證畫面呈現車架號未找到；異常後持續檢查的行為已由 F36 確認。人工配合畫面以圖示／實物部件圖、指令、訊號偵測與數字狀態呈現操作；HMI 短按測試顯示各按鍵成功次數。倒數／逾時與判定門檻尚待確認；偵測異常後的流程見 F36。
- **O08（證據界線，2026-09-22）**：A30 顯示 HMI 按鍵測試也需要人工配合，與 F33 回饋中「只有速度／踏頻／扭力測試需操作」的敘述範圍不同。保留兩方來源，可能涉及體驗範圍或版本，尚不推定原因；案例使用「多數自動化，部分檢查需要技師配合」，不使用絕對化描述。

- **F35（用戶確認，2026-09-22）**：Full Diagnosis 四分類由用戶與團隊共同重新整理，目的是讓技師理解，同時確認在技術上可行；診斷仍有必要的先後順序。不能歸因為用戶獨自決定，也不能描述為完全移除診斷順序。
- **F36（用戶確認，2026-09-22）**：Full Diagnosis 發現異常時先記錄並繼續檢查，不要求先解決異常才能往下。全部檢查完成後彙整結果（A26）；關閉 Full Diagnosis 回到 Overview 時，問題也同步列於 Workspace。此規則指診斷中發現異常的處理，不延伸推定斷線等執行失敗的行為，也不覆蓋維修操作本身的必要先後依賴。

- **F37（用戶回述，2026-09-22，A30–A31）**：最初 HMI 操作只用 power button 等名稱說明，卻發現連公司內部也有人無法辨識對應按鍵。用戶為所有不同款 HMI 繪製帶 A/B/C/D 等字母對應的部件圖，工程師依此安排檢測順序，設計目的為讓使用者直覺辨識當下要操作的按鍵。內部觀察不等同正式技師測試，尚無改善幅度數據。
- **F38（用戶回述，2026-09-22，A32）**：用戶認為感測器診斷是手動輔助中最複雜的部分，因此在開始前以插畫明確區分操作部位與感測器位置，避免技師把操作位置誤認為故障部件，進而更換錯誤零件。這是設計目的，未確認實際換錯零件事件或錯誤率改善。

### Knowledge Base、內容模板與售服銜接

- **F39（用戶回述，2026-09-22）**：團隊採用 Zendesk 建置 Knowledge Base，考量包含文章管理與工單系統。所有操作指引與排解指南最後一步提供聯絡 Hyena 團隊的入口，操作異常也可透過 give up and report 填寫表單；回報自動附帶車輛目前資訊並串接 Zendesk 工單，技師可在 Service Tool 內提出詢問，售服集中管理。尚未細分附帶欄位、後續回覆渠道或回覆時間，不推定完整操作紀錄會傳送，也不將 Zendesk 選型歸於用戶個人。
- **F40（用戶回述，2026-09-22）**：用戶主要負責建立內容 template 及確認整體流程，使售服可擴充步驟、加入媒體並應用必要的檢測模組；實際文件內容規劃高度與 marketing 團隊協作，確認文章分類及撰寫層次。不表述為用戶獨自撰寫全部技術內容或實作串接。
- **O09（畫面觀察，2026-09-22，A33–A35）**：完整指南呈現 Description、Potential Impact、Troubleshooting、檢測按鈕、影片及最後的求助步驟；另一畫面顯示復原失敗後可重試或回報，第三張為序號驗證情境的回報表單。三張可支持不同求助入口，但不是同一問題從頭到尾的連續截圖；自動帶入車況依 F39，而非由表單截圖推定。

### 候選 Key Decisions

以下四項為依現有資料整理的候選，排序為目前敘事安排，非成效排名；可依新資料重整。

1. **先完成問題盤點，再安排修復**
   - 問題與選擇：舊版遇到問題容易卡住；新版保留必要檢測順序，異常先記錄並繼續，分類彙整後同步至 Workspace，讓診斷與處理順序分開。
   - 個人作用與涵蓋功能：用戶與團隊共同整理技師可理解、技術可行的四分類；涵蓋連車檢查、Full Diagnosis、結果摘要及 Workspace。其他流程決策的個人主導範圍待補。
   - 依據／缺口：F05–F10、F17–F20、F24、F33–F36；A01–A03、A08、A24–A28。分類有正面回饋，尚缺採用此流程的協作與取捨細節，不宣稱已量化改善。

2. **以當前待辦為優先，同時保留工具入口**
   - 問題與選擇：任務看板藏住工具，工具並列又弱化任務優先度；用戶探索 wireframe 並吸收支援團隊回饋，形成左側工具、中央內容、右側 Workspace，將歷史紀錄移至 Service Book。
   - 個人作用與涵蓋功能：用戶進行布局探索與調整；涵蓋 Overview、工具導覽、Workspace、Service Book。Service Book 僅簡述資訊分工，Service Report 可作流程收尾。
   - 依據／缺口：F08、F20、F22、F25–F28、F32；A05、A08–A12、A18–A23。替代方案與回饋已有依據；Service Book 查看／輸出數量不高，不寫成使用成效成功。

3. **將問題說明、處理工具與售服求助串成可延續的流程**
   - 問題與選擇：舊版說明受彈窗限制、排解資源分散；任務直接連到可操作的內容，透過可擴充模板容納步驟、媒體與檢測模組，自行處理不足時可在工具內回報並帶入車輛資訊，轉為 Zendesk 工單。
   - 個人作用與涵蓋功能：用戶建立模板、確認整體流程，與 marketing 協作文章分類及撰寫層次，供售服擴充內容；涵蓋 Workspace、更新操作、排解指南、Knowledge Base、異常回報與售服交接。Zendesk 選型及串接不歸為用戶獨立完成。
   - 依據／缺口：F06–F08、F20–F21、F24、F31–F32、F39–F40；A13–A17、A22–A23、A33–A35。已有對問題說明與工具整合的好評；模板的規範取捨、可擴充程度仍待探索，沒有減少工單或縮短處理時間的成效證據。

4. **用實體部件對照，連接畫面理解與硬體操作**
   - 問題與選擇：技師跨品牌工作且未必熟悉 e-bike，內部也曾認不出 power button；以車圖定位、各款 HMI 字母對照及感測器插畫，區分操作位置與檢測部件。
   - 個人作用與涵蓋功能：用戶提出車圖理由、繪製各款 HMI 對照並堅持操作／感測器位置區分，工程依此安排檢測；跨 Overview、HMI 測試與 Sensor Diagnosis。
   - 依據／缺口：F23、F37–F38；A08–A09、A29–A32。屬軟硬體整合主題，依用戶要求精簡呈現，不歸為 Full Diagnosis 的功能子項，也不以小優化湊核心數量；尚無辨識或誤換率改善數據。

成果依 F28–F33 分別呈現：Workspace 任務解決率 93% 無舊版基準；經銷商與展會回饋屬質性證據；Service Book 使用情況有侷限。反思仍待用戶提供，不從數據代寫心得。
